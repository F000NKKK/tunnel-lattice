# Архитектура Tunnel Lattice

Tunnel Lattice создаёт и настраивает виртуальные интерфейсы TUN/TAP и
передаёт через них пакеты. Назначение IP-адресов на созданный интерфейс —
задача `net-lattice` (соседний крейт экосистемы Lattice), а не этого крейта.

## Карта крейтов

```text
tunnel-lattice-core             ошибки, ID — без зависимости от ОС
tunnel-lattice-model             DeviceKind/DeviceConfig/Device/DeviceConfigPatch — без зависимости от ОС
tunnel-lattice-platform          обобщённые provider-трейты + Capability — зависит только от core, никогда от model
tunnel-lattice-backend-tunrs     реализация platform-трейтов поверх tun-rs
tunnel-lattice-backend-linux     нативный Linux-backend (/dev/net/tun + синхронный rtnetlink) — в разработке, публичного API пока нет; вне Linux пустой
tunnel-lattice-async             адаптер futures::Stream поверх синхронного PacketIo-устройства
tunnel-lattice                   фасад: связывает platform-трейты с типами model, выбирает backend
```

Направление зависимостей: `core` ← `model`, `core` ← `platform`; `model` и
`platform` никогда не зависят друг от друга напрямую — именно
`tunnel-lattice-backend-tunrs` и фасад `tunnel-lattice` связывают обобщённые
associated types `platform` с конкретными типами `model`. Это то же правило,
что и «`net-lattice-platform` никогда не зависит от `net-lattice-model`» в
соседней экосистеме, и по той же причине: backend или фасад решают, какие
конкретные типы удовлетворяют контракту, а не сам контракт.

Правила, которые называют типы `model`, но одинаковы для любого backend'а,
живут в `tunnel-lattice-model` за не включаемым по умолчанию feature
`backend` (`tunnel_lattice_model::backend`), так что каждый backend хранит
только нативные вызовы и реализации трейтов: правила имён интерфейсов по ОС,
проверки, которые `open` выполняет до любого нативного вызова, правило запроса
segmentation offload, правила флагов и статуса административного состояния и
контракт `apply` (порядок проверок, порядок шагов, компенсация). Это
поддерживающий API для авторов backend'ов без обещаний стабильности; фасад
`tunnel-lattice` никогда не включает его и не реэкспортирует, и он не
выполняет ввод-вывод.

Правила, которые не называют типы `model`, живут так же в
`tunnel-lattice-platform` за его собственным не включаемым по умолчанию
feature `backend` (`tunnel_lattice_platform::backend`): шаг, который цикл
`recv`/`send` делает после одной нативной попытки, дренаж `recv_batch`
(обобщённый по типу ошибки чтения, классификатор передаётся замыканием) и
сырые коды ошибок, включая таблицу Linux `errno`, которая сопоставляет код и
операцию, его породившую, с исходом. Это безопасный Rust без зависимости от
`libc` (константы Linux сверяются с `libc` в собственных тестах крейта); у него
тот же статус без обещаний стабильности, и фасад так же никогда не включает и
не реэкспортирует его.

Кодек и движок segmentation offload для Linux на уровне очереди (см.
«Segmentation offload» ниже) живут в том же крейте за ещё одним не
включаемым по умолчанию feature `offload`
(`tunnel_lattice_platform::backend::offload`, подразумевает `backend`):
безопасный Rust, который компилируется и тестируется на любом хосте,
обобщён по типу ошибки чтения; нативные чтения, записи и классификацию
ошибок передаёт backend, сохраняющий вызовы `unsafe`.
`tunnel-lattice-backend-tunrs` включает его только для целей Linux.

## Почему это отличается от net-lattice

`net-lattice` инспектирует и изменяет объекты ОС (маршруты, интерфейсы,
настройки DNS), существующие независимо от вызывающего процесса — маршрут
существует вне зависимости от того, следит ли за ним какой-либо процесс,
поэтому `net-lattice-platform` разделяет чтение (`RouteProvider`) и запись
(`RouteMutator`) по доменам, а фасад держит одно постоянное соединение
(`Lattice<Backend>`), используемое для множества вызовов по ID объекта.

У TUN/TAP-устройства нет такого независимого существования: оно существует
только потому, что его создал текущий процесс, и только этот процесс держит
единственный дескриптор. Поэтому:

- нет отдельного шага «подключения» перед открытием устройства — открытие
  и есть привилегированная операция (`DeviceProvider::open`, а не
  `Lattice::connect` с последующими вызовами по ID);
- возвращённый дескриптор устройства сам является целью каждой последующей
  операции (`PacketIo`, `DeviceObserver`, `DeviceMutator`), а не ID,
  передаваемым в общий объект соединения;
- нет доменного чтения «список всех устройств», как у `RouteProvider` для
  маршрутов — backend, способный перечислить уже существующие постоянные
  устройства, предоставляет это как собственный inherent API, за флагом
  `Capability::PERSISTENT_DEVICES`, а не как обязательный метод трейта.

## План замены backend'а

`tunnel-lattice-backend-tunrs` оборачивает крейт `tun-rs`, который сам по
себе кроссплатформенный (Linux, Windows, macOS, BSD, iOS, Android) — в
отличие от взаимоисключающих backend'ов net-lattice для каждой ОС
(`net-lattice-backend-linux`/`-windows`/`-darwin`, каждый за `target_os`
cfg), Tunnel Lattice начинает с одного общего крейта backend'а, поскольку
пока нет платформенно-специфичного Rust-кода, который нужно изолировать —
`tun-rs` уже сделал эту работу внутри себя.

Воркспейс намеренно устроен так, чтобы `tun-rs` можно было убрать позже, не
трогая публичный API `tunnel-lattice-platform` или фасада `tunnel-lattice`:

- трейты `tunnel-lattice-platform` (`DeviceProvider`, `PacketIo`,
  `DeviceObserver`, `DeviceMutator`, `AsyncPacketIo`) не называют ни одного
  типа `tun-rs` — они обобщены через associated types, которым сегодня
  удовлетворяют `tunnel-lattice-backend-tunrs::TunRsBackend`/`TunRsDevice`;
- фасад выбирает backend через Cargo-**фичу** (`tun-rs`, включена по
  умолчанию), а не через `target_os` cfg. Будущий написанный вручную
  backend для конкретной ОС (например, `tunnel-lattice-backend-linux`
  напрямую поверх `/dev/net/tun` + Netlink, по аналогии с использованием
  Netlink в `net-lattice-backend-linux`) поставлялся бы отдельным крейтом
  со своей фичой фасада, выбираемой *наряду* с `tun-rs`, а не только взамен
  целиком — вызывающий сможет подключить `tunnel-lattice` с
  `default-features = false, features = ["linux-native"]`, когда это
  появится;
- любой backend, включая написанный вне этого воркспейса или тестовый
  двойник, подставляется через `Tunnel::new(backend)` — фича `tun-rs`
  лишь добавляет `Tunnel::connect()` как сокращение для
  `Tunnel::new(TunRsBackend::new())`. `Tunnel::capabilities()` сообщает
  возможности хоста до открытия устройства (например, найден ли драйвер
  TAP), но `open` остаётся авторитетным. `Handle::id()` и `Handle::kind()`
  не делают нативных вызовов: идентификатор фиксируется при открытии
  (`DeviceObserver::id`) и не обязан совпадать с текущим индексом
  интерфейса в ОС, поэтому для связи с `net-lattice` интерфейс ищется по
  имени;
- когда backend для конкретной ОС покроет все платформы, которые сегодня
  покрывает `tun-rs`, отказ от фичи `tun-rs` (и самой зависимости) станет
  изменением только в крейте backend'а — ничего в `tunnel-lattice-model`
  или `tunnel-lattice-platform` переносить не придётся.

Первый backend для конкретной ОС, `tunnel-lattice-backend-linux`, в
разработке: крейт уже есть (только Linux, на других целях пустой) и содержит
отображение сырых errno в ошибки, синхронный control plane на rtnetlink и
синхронное ядро устройства, внутренне реализующее provider-трейты: открытие
TUN- и TAP-устройств через `TUNSETIFF` с `IFF_NO_PI` (неблокирующий
дескриптор с момента создания, индекс интерфейса как id устройства, узел
устройства никогда не создаётся), packet I/O через `readv` с однобайтовым
sentinel для обнаружения слишком больших пакетов и отправку с попыткой
записи сразу, snapshot и apply через rtnetlink с откатом по возможности,
persistence и multi-queue — с тем же набором Linux-capability, что и у
`tunnel-lattice-backend-tunrs`. Публичного API он пока не экспортирует,
асинхронного I/O и segmentation offload нет, и ни одна фича фасада его не
выбирает. До тех пор этот раздел фиксирует намеченную форму, а не
выполненную работу.

## Модель ошибок

Повторяет `net-lattice-core::Error`: один `#[non_exhaustive]` enum
(`PermissionDenied`, `NotFound`, `AlreadyExists`, `Unsupported`,
`InvalidState`, `Disconnected`, `DriverUnavailable`, `BufferTooSmall`,
`Platform(PlatformErrorCode)`),
возвращаемый каждым методом provider-трейта вместо «сырой» ошибки ОС.
Backend отображает свою нативную ошибку (сейчас — `std::io::Error` для
`tun-rs`) в эту форму на границе; вызывающий код никогда не сопоставляет
паттерн напрямую с `errno`/`DWORD`.
`tunnel-lattice-backend-tunrs` сначала отображает переносимый
`io::ErrorKind` (`PermissionDenied`, `NotFound`, `AlreadyExists`,
`Unsupported`, а `BrokenPipe`/`UnexpectedEof`/`NotConnected` → `Disconnected`);
только виды без типизированного аналога попадают в
`Platform(PlatformErrorCode)`.
`PlatformErrorCode` сам помечен `#[non_exhaustive]` (`Linux(i32)`,
`Windows(u32)`, `Darwin(i32)`, `Unknown`): нативный сбой без кода ошибки
ОС, а также сбой на платформе, для которой нет своего тега, сообщается как
`Platform(PlatformErrorCode::Unknown)` — а не выдуманный код `0`, который
на любой платформе означал бы «успех».

`DeviceProvider::open` добавляет перед этим отображением два слоя.
Во-первых, предварительные проверки отклоняют с `InvalidState` запрошенное
имя (формат зависит от ОС и описан в `DeviceConfig::name`) или MTU, которые
платформа не может принять, — до любого нативного вызова. Во-вторых,
классификатор, работающий только в `open`, превращает в типизированные
варианты нативные ошибки, имеющие особый смысл лишь при создании
устройства: отсутствие драйвера или user-mode рантайма (`wintun.dll`,
драйвер tap-windows6, модуль `tun` в Linux) становится `DriverUnavailable`,
который не возвращает ни одна другая операция; существующий интерфейс с
запрошенным именем становится `AlreadyExists` (в Linux и macOS — только если
интерфейс с таким именем действительно существует, поскольку тот же errno
означает и другие сбои). Всё остальное проходит через общее отображение.
`open` никогда не подхватывает существующий интерфейс, чтобы затем удалить
его при drop: бэкенд `tun-rs` отключает в macOS/Windows поведение `tun-rs`
по умолчанию «переиспользовать существующее TAP-устройство», а два
оставшихся случая подключения — постоянные или multi-queue устройства в
Linux и существующие адаптеры Wintun в Windows — задокументированы, а не
запрещены: ни один из них не удаляет интерфейс, а проверка перед открытием
была бы подвержена гонке с другими процессами.

Свой слой есть и у `recv`. Он никогда молча не обрезает пакет и никогда не
сообщает больше байт, чем вмещает буфер: пакет, который не помещается,
отбрасывается, `recv` возвращает `BufferTooSmall`, а устройство остаётся
пригодным к работе. Нативное поведение зависит от ОС: Linux TUN/TAP и
macOS `utun` молча обрезают пакет, поэтому бэкенд `tun-rs` читает в буфер
вызывающего кода плюс однобайтовый буфер-«сторож» и считает длину больше
буфера признаком того, что пакет не поместился; macOS TAP (`feth`) и
Windows (Wintun, tap-windows6) отклоняют пакет ошибкой, которую бэкенд
отображает в `BufferTooSmall`. `Device::recv_buffer_len()` (MTU для TUN,
MTU + 18 для TAP: заголовок Ethernet и один тег 802.1Q) даёт буфер, в
который помещается любой пакет при MTU из снимка, кроме кадра TAP с
двойным тегом (QinQ). Кроме того, `recv` и `send` сами
повторяют вызов при двух временных условиях, не сообщая о них: `EINTR` в
Linux и macOS и чтение macOS TAP, не давшее ни одного целого кадра
(`tun-rs` сообщает о нём как о конце файла с особым сообщением). Любой
другой конец файла остаётся `Disconnected`.
На очереди TUN в Linux, использующей segmentation offload (см. ниже
«Segmentation offload»), `recv` также молча отбрасывает и перечитывает ещё
два случая: «сырой» `EINVAL` при чтении (ядро отказалось оформить пакет и
уже освободило его) и принятый кадр, не прошедший проверку. Ни один из
них не сообщается, поэтому новый вариант ошибки не нужен и поток не
завершается. На такой очереди `BufferTooSmall` отбрасывает один сегмент,
а не один пакет.

Кроме того, `recv` и `send` распознают устройство, которое удалили или
отключили из-под дескриптора. `Disconnected` означает, что канал
устройства исчез навсегда: «сырой» `ENXIO` (macOS — BPF-дескриптор TAP
после уничтожения парного `feth`, к которому он привязан; в Linux
отображается для симметрии), `EBADFD` в Linux (файл tun отсоединён,
потому что устройство удалено), `EFAULT` в Linux только при `recv`
(блокирующее чтение, уже ожидавшее в момент удаления устройства) и сигнал
Wintun «адаптер завершает работу» при отправке в Windows. Отключённый
адаптер Wintun
(например, после применения `DesiredAdminState::Down`) сообщает
`InvalidState`, потому что применение `Up` восстанавливает тот же
дескриптор; так же ведёт себя `send` в Linux на административно
выключенном TUN/TAP-устройстве: драйвер tun возвращает «сырой» `EIO` при
записи только в этом случае. На TAP-дескрипторе Windows применение `Down`
отключает среду передачи адаптера, после чего tap-windows сразу завершает
каждый `send` и `recv`, сделанный, пока среда отключена, «сырым» кодом
`ERROR_OPERATION_ABORTED` (995); этот код становится `InvalidState`
только на TAP-дескрипторе (правило учитывает не только ОС, но и тип
устройства), поскольку применение `Up` восстанавливает тот же
дескриптор. Чтение, уже ожидавшее в момент применения `Down`, не
прерывается: как на выключенном устройстве Linux, оно продолжает ждать и
после `Down`, и после последующего `Up`, и завершает его только
отключение адаптера. Исправный TAP-адаптер тоже возвращает
995 для чтения, отменённого из-за завершения потока, который его начал
(асинхронный `recv` начинает чтение в опрашивающем потоке, поэтому
сброшенный `recv`, поток которого затем завершился, оставляет такое
чтение). Поэтому при `recv` первый код 995 в вызове один раз повторяется
новым чтением, если операционное состояние адаптера читается как up;
состояние читается не более одного раза за вызов. Один вызов, встретивший
два отменённых чтения, на исправном адаптере однократно сообщает
`InvalidState`. `send` не повторяется, потому что `tun-rs`
отбрасывает отменённую незавершённую запись. `InvalidState` от
`recv`/`send` означает «устройство существует, но не передаёт пакеты,
потому что выключено или отключено»; если причиной был `apply(Down)`, то
`apply(Up)` на том же дескрипторе его восстанавливает. На выключенном
устройстве Linux `recv` не завершается ошибкой, а ждёт, а выключенное
устройство macOS по-прежнему принимает `send`. TAP-адаптер Windows,
отключённый вне крейта (`Disable-NetAdapter`), завершает вызовы тем же
кодом и поэтому тоже сообщает `InvalidState`, хотя восстановить его может
только повторное включение вне крейта. Эти правила сравнивают «сырые»
коды ОС только на той ОС, которой они принадлежат, а ошибку с «сырым»
кодом никогда не сопоставляют через `kind()` (`std` декодирует его по
таблице кодов ОС, на которой выполняется код); по виду и сообщению
сопоставляются только ошибки Wintun без кода ОС. Поэтому каждое правило
проверяется юнит-тестами на любом хосте.

Оба варианта `PacketStream` выдают `BufferTooSmall` и продолжают приём.
Любая другая ошибка выдаётся один раз, после чего поток завершается —
и `Disconnected`, и восстановимые ошибки. Иначе устройство, чей `recv`
сразу и раз за разом возвращает ошибку (удалённое устройство Linux,
уничтоженный `feth` в macOS, отключённый адаптер Wintun), превратило бы
поток в холостой цикл из ошибок, а в потоковом мосте — заставляло бы
рабочий поток крутиться вхолостую; задержка между попытками потребовала
бы таймера (крейт не привязан к рантайму), а предел числа ошибок —
произвольного числа. После восстановления вызывающий код создаёт новый
поток через `Handle::packet_stream`. Временные условия до потока не
доходят, потому что бэкенд повторяет вызов сам; поэтому повтор при
`EINTR` и повтор отменённого чтения TAP в Windows обязательны: без них
сигнал или чтение, отменённое завершившимся потоком, завершали бы
исправный поток. `BufferTooSmall` остаётся единственной ошибкой, которая
не завершает поток, на любой ОС.

У `DeviceMutator::apply` один контракт для всех бэкендов. Все предусловия
он проверяет до любого нативного вызова:

- патч для другого устройства, MTU больше `u16::MAX` или MAC-адрес для
  TUN-устройства — `InvalidState`;
- затем настройка, которую бэкенд не умеет применять, например MAC-адрес
  на дескрипторе без `Capability::MAC_MUTATION`, — `Unsupported`.

Затем он применяет MTU, потом MAC-адрес, потом административное
состояние. Состояние идёт последним, чтобы после него не мог упасть ни
один шаг и его никогда не приходилось откатывать. Если шаг завершается
ошибкой, уже применённые шаги откатываются в обратном порядке по
возможности, и возвращается собственная ошибка упавшего шага. Чтобы откат
был возможен, прежние MTU и MAC читаются заранее, но только если дальше
есть ещё шаг. Ошибки `PartiallyApplied` нет: после любого `Err`
авторитетен `snapshot()`. Поэтому `InvalidState` всегда означает, что
отклонено предусловие и ничего не изменилось, — то же правило, что в
`net-lattice`.

У TAP-устройства есть MAC-адрес, у TUN — нет. `Device::mac` сообщает его
для TAP (`None` для TUN), `DeviceConfig::with_mac` запрашивает адрес при
открытии, `DeviceConfigPatch::with_mac` меняет его позже. `MacAddress` —
чистые данные той же формы, что и в `net-lattice-model`, поэтому они
конвертируются друг в друга через `[u8; 6]`. MAC, запрошенный для
TUN-устройства, отклоняется с `InvalidState` до создания чего-либо. После
открытия бэкенд читает адрес обратно; если платформа его не применила,
`open` возвращает `Unsupported`, а новое устройство удаляется. Для
последующей смены нужен `Capability::MAC_MUTATION`: бэкенд `tun-rs`
сообщает его для TAP-дескриптора в Linux и macOS. В Windows драйвер
tap-windows6 берёт адрес из настроек адаптера в реестре при его создании,
поэтому адрес можно запросить при открытии, но нельзя сменить потом.

## Контракт владения и конкурентности

`tunnel_lattice::Handle<D>` оборачивает бэкенд-устройство в `Arc<D>` и сам
реализует `Clone` (дешёвый `Arc::clone`, а не дублирование устройства) — это
осознанный явный контракт, а не деталь реализации, используемая только
внутри `packet_stream`:

- **Несколько читателей/писателей, разделяющих один клон `Handle`, всегда
  безопасны на любом backend'е.** `PacketIo::recv`/`send` принимают `&self`
  — это проверено напрямую по сигнатурам самого `tun-rs` на Linux, macOS и
  Windows (везде `recv`/`send` объявлены как `fn(&self, ...)`), а сессии
  Wintun на Windows официально документированы как потокобезопасные для
  конкурентных вызовов `WintunReceivePacket`/`WintunSendPacket` — именно
  поэтому это работает без какой-либо особой обработки с нашей стороны. Это
  не гейтится никакой фичей или capability — совместное использование
  одного клона `Handle` из нескольких потоков с параллельными
  `recv`/`send` и есть базовый, переносимый сценарий мультиплексирования.
  Привилегированный CI проверяет это на настоящем TUN-устройстве на Linux,
  macOS и Windows во всех трёх наборах фич: устройству назначается адрес,
  один клон блокируется в `recv`, пока другой клон пишет ICMP echo-запросы
  от адреса пира, и echo-ответ хоста, направленный обратно в то же
  устройство, должен дойти до ожидающего `recv` за 60 секунд (с
  `async-io`/`tokio` — ещё и с задачей `packet_stream` на одном клоне и
  `send_async` на другом). На Windows тест добавляет правило брандмауэра,
  пропускающее echo-запросы к адресу устройства, и потом удаляет его.
- **`Handle::additional_queue`** (доступен при `D: MultiQueueProvider`, см.
  ниже) — это *другое, более сильное* средство: независимый `Handle` над
  второй, аппаратно-распределяемой очередью, а не вторая ссылка на ту же
  самую. Два `Handle`, полученных так, не делят `Arc`: удаление одного не
  влияет на другой.
- **Drop закрывает устройство только тогда, когда исчезает последний клон**
  (`Handle` или `PacketStream`) его `Arc`, через собственный `Drop`
  реализации `D` (`tun_rs::SyncDevice`/`AsyncDevice` закрывают там файловый
  дескриптор). Явного метода "закрыть" нет — единственный способ — дать
  упасть каждой ссылке, а `PacketStream`, созданный из `Handle`, хранит
  собственный клон `Arc`, независимый от исходного `Handle`, поэтому любой
  из них может пережить другой.

См. rustdoc самого `tunnel_lattice::Handle` за полным контрактом; этот
раздел существует, чтобы ответ на вопросы "кто владеет устройством, можно
ли им делиться, что происходит при drop" был зафиксирован до `1.0`, а не
оставался неявным в коде, который для этого пришлось бы читать.

## Постоянные устройства и multi-queue

`Capability::PERSISTENT_DEVICES` (`tunnel_lattice_platform::PersistentDevice`)
и `Capability::MULTI_QUEUE` (`tunnel_lattice_platform::MultiQueueProvider`)
в `tunnel-lattice-backend-tunrs` доступны только на Linux — это проверено
непосредственно в исходниках `tun-rs`, а не предполагается: `DeviceImpl::
persist`, `DeviceBuilder::multi_queue` и `SyncDevice`/`AsyncDevice::
try_clone` — все `#[cfg(target_os = "linux")]` в самом `tun-rs`, без
какого-либо аналога на macOS/Windows вообще (не просто "игнорируются" —
этих методов там попросту не существует). Оба трейта в
`tunnel-lattice-platform` объявлены безусловно, поскольку сам контракт
универсален; гейтится только реализация в `tunnel-lattice-backend-tunrs`
(`#[cfg(target_os = "linux")]`).

- **Персистентность** (`Handle::persist`, `Handle::unpersist`) помечает
  открытое устройство как переживающее закрытие последнего дескриптора (в
  том числе завершение процесса) и снимает эту пометку, после чего
  устройство уничтожается, как только закроется его последний дескриптор в
  любом процессе. Оба вызова — это ioctl ядра `TUNSETPERSIST`, аргумент
  которого передаётся по значению: ненулевой устанавливает `IFF_PERSIST`,
  ноль сбрасывает. `persist` идёт через `tun-rs`; сбросить флаг `tun-rs`
  не умеет, поэтому `unpersist` сам выполняет `TUNSETPERSIST(0)` на
  дескрипторе устройства одним задокументированным `unsafe`-вызовом и
  передаёт ноль как целое число, а не указатель
  (указатель на ноль ненулевой и установил бы флаг). Ядро не проверяет
  привилегии для этого ioctl: достаточно дескриптора, подключённого к
  устройству, а для его получения обычно нужны `CAP_NET_ADMIN` или права
  владельца устройства. Оба вызова работают с любой очереди. Подключение к
  существующему персистентному устройству по имени не требует отдельного
  API: это обычное поведение ядра Linux при `TUNSETIFF` по имени —
  достаточно открыть устройство с тем же `DeviceConfig::name`, типом и
  `multi_queue`. Ядро подключается к любому существующему устройству того
  же типа и с той же настройкой multi-queue (в том числе, при multi-queue,
  к работающему устройству, открытому другим процессом), отклоняет
  несовпадение типа или multi-queue с `EINVAL`, а устройство без
  multi-queue, у которого уже есть очередь, — с `EBUSY` (оба случая
  возвращаются как `Error::AlreadyExists`); при этом `open` не может
  сообщить, подключился он или создал новое устройство. Отдельное
  задание CI проверяет весь цикл в двух процессах: первый создаёт
  устройство, делает его персистентным и завершается, второй подключается
  по имени, снимает персистентность и закрывает его, после чего устройства
  больше нет.
- **Multi-queue** (`DeviceConfig::with_multi_queue`, `Handle::
  additional_queue`) запрашивает `IFF_MULTI_QUEUE` при открытии и, если
  запрос удовлетворён, дублирует по-настоящему независимую,
  аппаратно-распределяемую очередь на том же устройстве (`try_clone` у
  `tun-rs`) — в отличие от "наивной" мультиплексации выше, которая вообще
  не требует запроса multi-queue и работает на любой платформе. Вызов
  `additional_queue` на устройстве, открытом без `with_multi_queue(true)`,
  возвращает `Error::Unsupported` (полученный из `io::ErrorKind::
  Unsupported` самого `tun-rs` — переносимый сигнал, отличный от сырого
  кода ошибки ОС, в отличие от остальных случаев `Error::Platform` в этом
  крейте). Очередь, подключённая к существующему многоочередному
  устройству, и каждая `additional_queue` получают формат кадров
  устройства, который backend считывает после открытия (см. следующий
  раздел).

## Segmentation offload (TUN в Linux)

`DeviceConfig::offload` (`with_offload`, по умолчанию выключен) запрашивает
segmentation offload ядра. Как и `multi_queue`, это запрос, а не гарантия:
backend `tun-rs` выполняет его только для TUN-устройств в Linux и молча, без
ошибки, игнорирует на Windows, macOS и для TAP (нарезка разбирает только
IP, но не Ethernet). Ответом служит `Capability::SEGMENTATION_OFFLOAD`,
который сообщается только у дескриптора и никогда — на уровне хоста в
`Tunnel::capabilities()`. Offload фиксируется при открытии: в
`DeviceConfigPatch` для него нет поля, и `apply` его не трогает.

Со стороны ядра это 10-байтовый заголовок virtio-net перед каждым пакетом
очереди (`IFF_VNET_HDR`) плюс общая для устройства маска offload
(`TUNSETOFFLOAD`), которая позволяет ядру отдавать один TCP- или
UDP-суперпакет размером до 64 КиБ вместо многих пакетов и принимать такой
же при записи. Tunnel Lattice сам разбирает и собирает этот заголовок в
модуле, который не выполняет ввода-вывода, использует только проверяемую
арифметику и компилируется и проходит модульные тесты на любой ОС (это
`backend::offload` крейта `tunnel-lattice-platform` за feature `offload`;
backend добавляет только нативные чтения и записи); из
`tun-rs` используются только публичная опция builder'а и векторные чтение
и запись, но не его скрытые вспомогательные функции offload. Формат
пакетов, который видит вызывающий код, не меняется:

- **Приём.** `recv` (синхронный и асинхронный) по-прежнему возвращает
  ровно один IP-пакет без заголовка, поэтому `PacketStream`, `PacketPool`
  и правило «один элемент — один пакет» не затронуты. Каждая очередь с
  offload владеет буфером подготовки (заголовок + 65 536 байт +
  однобайтовый «сторож», около 64 КиБ, выделяется только для очереди с
  offload) и курсором нарезки под мьютексом. `recv` выдаёт следующий
  ожидающий сегмент прямо в буфер вызывающего кода (заголовки исправлены,
  полезная нагрузка скопирована один раз, контрольные суммы дописаны);
  следующий суперпакет читается, только когда ожидающих сегментов нет.
  Асинхронные пути никогда не держат блокировку через await, и между
  успешным чтением и возвратом нет ни одного await, поэтому удалённый
  future `recv` никогда не теряет прочитанный суперпакет: невыданные
  сегменты ждут следующего вызова. Нарезка при приёме ограничена только
  длиной кадра, а не числом сегментов, поэтому TCP-суперпакет с малым MSS
  никогда не отбрасывается. `recv_batch` выдаёт ожидающие сегменты в
  соседние буферы и читает следующие суперпакеты без ожидания (см.
  «Асинхронный дизайн»), так что один вызов может вернуть целый
  суперпакет или несколько. Сегмент, не помещающийся в свой буфер после
  первого, там не отбрасывается: он завершает пакетный приём и остаётся
  ожидающим. Кадр, отвергнутый нарезкой, или «сырой» `EINVAL`, встреченные
  при дочитывании, отбрасываются, и дочитывание продолжается.
- **Отправка.** `send` пишет пакет за нулевым заголовком. `send_batch`
  склеивает серии соседних пакетов одного потока (TCP с непрерывными
  номерами последовательности и в остальном одинаковыми заголовками или
  UDP с датаграммами одного размера, если ядро принимает UDP segmentation
  offload) в одну запись `[заголовок, исправленная копия заголовков первого
  пакета, срезы полезной нагрузки...]` без аллокаций и без копирования
  полезной нагрузки. Один вызов обрабатывает не больше 128 пакетов
  (предел ядра на число сегментов в суперпакете) и при большем списке
  возвращает неполный `Ok`. Запись серии, отвергнутая с `EINVAL`, ничего не
  отправила и повторяется по одному пакету, поэтому ядро без нужного
  offload сводится к поштучной отправке.

Формат кадров следует устройству, а не запросу. `IFF_VNET_HDR` и размер
заголовка общие для устройства, а очередь, подключённая к многоочередному
устройству, у которого уже есть очереди, не получает собственных флагов,
поэтому после каждого открытия и `additional_queue` backend считывает
фактический формат (`TUNGETIFF`, `TUNGETVNETHDRSZ`): флаг заголовка
установлен и размер 10 — очередь с offload (даже без запроса); любой
другой размер — `open` завершается с `Error::Unsupported`; флаг сброшен —
обычная очередь (даже с запросом), и тогда backend сбрасывает маску
offload, выставленную запросом (`TUNSETOFFLOAD(0)`), потому что устройство
без заголовка ни для кого не должно выдавать суперпакеты. До 0.5
включительно обычная очередь, подключённая к многоочередному устройству с
offload, отдавала каждый пакет вызывающему коду с 10-байтовым заголовком
впереди.

Маска offload общая для устройства и даёт побочный эффект для других
очередей и процессов: открытие с offload выставляет её (контрольные
суммы, TSO для IPv4 и IPv6 и UDP-сегментацию, если она есть в ядре), а
`tun-rs` сбрасывает её при каждом открытии в Linux без offload, поэтому
обычное открытие общего многоочередного устройства с offload выключает
суперпакеты для всех его очередей. Они остаются правильно оформленными и
просто принимают одиночные пакеты. При удалении дескриптора ничего не
компенсируется: маска не восстанавливается, как и в `tun-rs`. Заголовок
декодируется в порядке байтов хоста; хост big-endian, устройство которого
кто-то другой переключил на little-endian-заголовки, не поддерживается и
не распознаётся. Проверки на этапе компиляции или минимальной версии ядра
нет: решает то, о чём ядро договорилось при открытии. Offload не требует
привилегий сверх тех, что нужны для открытия устройства.

## Асинхронный дизайн

Фича `async` крейта `tunnel-lattice-platform` добавляет `AsyncPacketIo` —
трейт, возвращающий `impl Future`, который backend реализует при наличии
настоящего неблокирующего ввода-вывода (файловый дескриптор,
зарегистрированный в асинхронном рантайме, overlapped I/O, ...).
`tunnel-lattice-backend-tunrs` реализует его напрямую на своём хендле
`tun_rs::AsyncDevice` (собранном через `DeviceBuilder::build_async`, а не
клонированном из отдельного синхронного хендла — `try_clone` у
`tun_rs::SyncDevice` существует только на Linux) и сообщает
`Capability::NATIVE_ASYNC`; блокирующая реализация `PacketIo` при этом
блокируется на тех же асинхронных методах, а не хранит второй хендл — но
конкретный способ блокировки зависит от того, какой из двух
взаимоисключающих асинхронных backend'ов активен, и разница существенна:
для `async-io` (`AsyncDevice`, собранный на рантайм-независимых крейтах
`async-io`/`blocking`) используется `futures::executor::block_on`, а для
`tokio` — обязательно `tokio::runtime::Handle::current().block_on`:
`futures::executor::block_on` никогда не опрашивает собственный I/O-драйвер
Tokio, поэтому `recv`/`send` на tokio-хендле иначе зависли бы навсегда в
ожидании уведомления о готовности, которое драйвер так и не доставит. Это
было найдено и исправлено через изолированное воспроизведение
непосредственно на `tun-rs` (подтверждено на реальном устройстве при
`CAP_NET_ADMIN`: `send()` завис дольше 10-секундного таймаута до
исправления и завершился мгновенно после). Это же означает, что фича
`tokio` требует **многопоточного** Tokio-рантайма на вызывающем потоке —
`Handle::block_on` опрашивает I/O-реактор рантайма только в варианте
`multi_thread`; на `current_thread` это делает лишь `Runtime::block_on`
(вызванный на самом значении `Runtime`, а не на `Handle`), поэтому
`current_thread`-рантайм воспроизводит то же зависание. См. README
`tunnel-lattice-backend-tunrs`, раздел "`tokio` requires a multi-threaded
runtime".

В Linux с `tokio` метод `recv` вообще не ждёт через `tun-rs`: он читает
через закрытый дубликат дескриптора устройства, зарегистрированный в Tokio
на готовность к чтению *и* на готовность-ошибку. Удалённое устройство
Linux сообщает только о готовности-ошибке, которую ожидание одной лишь
готовности к чтению (так ждёт `tun-rs`) не замечает, поэтому ожидающий
`recv` иначе завис бы, а не завершился бы с `Disconnected`. `send`
по-прежнему идёт через хендл `tun-rs`.

В macOS с `async-io` или `tokio` метод `recv` TAP-устройства (`feth`)
по-прежнему читает через `tun-rs`, но заменяет его ожидание готовности.
Уведомление о готовности BPF в macOS сообщает только о данных в буфере и
никогда — об исчезновении интерфейса, поэтому неограниченное ожидание
`tun-rs` на BPF-дескрипторе после уничтожения парного `feth` не
закончилось бы никогда. Вместо этого backend ждёт на дубликате этого
дескриптора в пуле потоков `blocking` (том же пуле, которым там пользуется
сам `tun-rs`, поэтому не нужны ни реактор, ни таймер рантайма) отрезками
не дольше 250 мс и по каждому таймауту спрашивает у ядра, к какому
интерфейсу привязан дескриптор; как только этот запрос завершается ошибкой,
следующее чтение возвращает `ENXIO`, который отображается в
`Disconnected`. Отдельный pipe на каждое ожидание позволяет отброшенному
`recv` сразу завершить ожидание своего потока, а внутри ожидания ни один
пакет не читается, поэтому отмена `recv` никогда не теряет пакет. Цена —
один дополнительный дескриптор на TAP-хендл и pipe на каждое идущее
ожидание; `send` и устройства `utun` не меняются.

`tunnel-lattice-async` даёт два способа собрать `futures::Stream`, который
возвращает `Handle::packet_stream`: `from_async_device` строит поток
напрямую из `AsyncPacketIo::recv` через `futures::stream::unfold` — без
рабочего потока вообще; `from_device` — исходный мост на блокирующем
`PacketIo` через рабочий поток, для backend'а без нативного асинхронного
пути. `Handle::packet_stream` выбирает между ними в рантайме, проверяя
`Capability::NATIVE_ASYNC` — поэтому новому backend'у не нужна собственная
асинхронность, чтобы получить поток вообще: одной реализации `PacketIo`
уже достаточно для работы через `from_device`, а `AsyncPacketIo` —
аддитивная оптимизация, которую `packet_stream` предпочитает автоматически,
а не то, что вызывающий код выбирает по имени.

Это различие не косметическое. Поток `from_async_device` *по-настоящему*
отменяем: его удаление роняет закешированный (boxed), опрашиваемый в данный
момент future `AsyncPacketIo::recv` — обычная, безусловная семантика drop
для future в Rust, ничего не остаётся работать дальше. У рабочего потока
`from_device` такой гарантии нет: удаление потока может лишь выставить
флаг, который поток проверяет *между* вызовами `recv`, поэтому воркер,
застрявший внутри блокирующего `recv` при отсутствии новых пакетов,
продолжает работать, пока само устройство его не разблокирует (это
остаётся задокументированным ограничением `from_device` для того
гипотетического backend'а, которому оно реально нужно — без нативного
асинхронного пути вообще; каждый backend, который сегодня поставляет
`tunnel-lattice`, реализует `AsyncPacketIo` всегда, когда `packet_stream`
вообще достижим, так что `from_device` не задействован ни в одной
поставляемой сборке). Границу `Handle::packet_stream` соответственно
ужесточили до `AsyncPacketIo` (раньше было достаточно `PacketIo`) —
pre-1.0 изменение, по сути аддитивное для каждого поставляемого backend'а.

Отправку одного пакета обслуживает один метод, `Handle::send_async`, под
теми же фичами (его пакетный вариант описан ниже).
Он возвращает собственный future устройства `AsyncPacketIo::send` без
изменений (объявлен как `impl Future<Output = Result<usize>> + Send`, а не
`async fn`, чтобы `Send` был частью контракта), без проверки возможностей,
без запасного пути и без преобразования ошибок: в backend'е tun-rs
блокирующий `send` блокируется на том же самом future, поэтому результаты
и ошибки у них одинаковы. Метод нужен потому, что блокирующий `send`
нельзя вызывать из асинхронного кода (с `tokio` он паникует внутри задачи
и зависает на `current_thread`; с `async-io` он занимает поток
исполнителя), а `Handle` не открывает доступ к своему устройству.
Backend без `Capability::NATIVE_ASYNC` всё равно должен сам реализовать
`AsyncPacketIo`, и его future отправки может блокировать опрашивающий
поток. `Sink` намеренно нет: `AsyncPacketIo::send` не основан на poll,
поэтому `Sink` потребовал бы упаковывать future в `Box` и владеть копией
пакета (или слотом пула) на каждый пакет, а описанная ниже схема буферов
существует как раз чтобы этого избежать; `Sink` можно построить поверх
`send_async` позже. Удалить future всегда безопасно, и часть пакета при
этом никогда не отправляется. По ОС с tun-rs: на Linux и macOS (`utun` и
`feth`) отправка, удалённая до завершения, ничего не отправила, потому что
запись происходит только в том poll, который её завершает; на Windows
tun-rs копирует пакет и пишет в своём пуле блокирующих потоков, поэтому
удалённая отправка могла уйти, а могла и нет. Переносимый контракт, также
записанный на `AsyncPacketIo::send` как обязательство backend'а: "весь
пакет не более одного раза; после удаления неизвестно".

Пакетная отправка аддитивна и устроена так же. `PacketIo::send_batch` и
`AsyncPacketIo::send_batch` — методы трейтов с реализацией по умолчанию
(обязательных методов не добавилось, и `PacketIo` остаётся
dyn-совместимым), которая отправляет пакеты по одному; `Handle::send_batch`
и, при асинхронных фичах, `Handle::send_batch_async` передают вызов
напрямую. Контракт — префикс без отложенных ошибок: `Ok(n)` значит, что
`packets[..n]` отправлены целиком и по порядку, а `packets[n..]` не
тронуты, и `n` может быть меньше длины списка, поэтому вызывающий код
повторяет вызов в цикле; пустой срез даёт `Ok(0)`; `Err(e)` значит, что
ничего не отправлено, и `e` относится к `packets[0]` и классифицирована так
же, как её классифицировал бы `send`; сбой после `k > 0` пакетов
превращается в `Ok(k)`, а следующий вызов, начиная с `packets[k]`, видит
ошибку. Удаление future `send_batch` расширяет правило для одного пакета:
отправлен неизвестный префикс, каждый пакет целиком и не более одного
раза, и никогда — пакет после неотправленного. Реализацию по умолчанию
переопределяет только очередь TUN с offload в Linux (см. выше
«Segmentation offload»); все остальные backend'ы, ОС и очереди отправляют
по одному пакету. `recv_batch`
зеркалирует это на приёме: ждёт только первый пакет, возвращает префикс и
сообщает ошибку после `k` пакетов следующим вызовом. Реализация по
умолчанию принимает ровно один пакет; backend `tun-rs` сохраняет её на
Windows и macOS. В Linux (TUN и TAP, любой набор фич) он переопределяет
её дочитыванием: первый пакет принимается ровно так же, как его принимает
`recv`, а каждая следующая позиция — одно чтение, которое никогда не ждёт
(`preadv2` с `RWF_NOWAIT` в блокирующей сборке, неблокирующее чтение уже
зарегистрированного дескриптора в асинхронных сборках, с `tokio` —
`try_io` на том же readiness guard), поэтому флаг `O_NONBLOCK`
дескриптора никогда не переключается под другим клоном дескриптора.
Дочитывание заканчивается на ёмкости, на пустой очереди (`EAGAIN`) или
чтении, которое не может обойтись без ожидания (`EOPNOTSUPP`), или на
любой другой ошибке, которую сообщит собственное чтение следующего
вызова; `EINTR` повторяет чтение. Обычный пакет, оказавшийся длиннее
своего буфера после первого, уже снят с очереди, поэтому пакетный приём
заканчивается перед ним, а следующий `recv` или `recv_batch` на этом
дескрипторе сначала один раз возвращает `BufferTooSmall` (флаг на
очередь). На очереди с offload каждая позиция берёт следующий сегмент из
буфера подготовки (см. выше «Segmentation offload»), а сегмент, не
помещающийся в свой буфер после первого, вместо этого остаётся ожидающим.
После первого пакета нет ни одного await, поэтому удалённый асинхронный
`recv_batch` ничего не принял. Само дочитывание написано через замыкания
чтения, без собственного ввода-вывода, и живёт в модуле `backend`
крейта `tunnel-lattice-platform`, так что его разделяют все backend'ы. `PacketStream` и `PacketPool` по-прежнему принимают
через `recv` на один пакет. Тип вне крейта, реализующий и `PacketIo`, и `AsyncPacketIo`,
должен явно указывать трейт при вызове `send_batch`, если оба трейта в
области видимости, — как и для `recv` и `send`.

### Буферы пакетов

`PacketStream` выдаёт `Result<PacketBuf>`. Каждый поток принимает пакеты в
`PacketPool`: один обнулённый slab, выделяемый один раз и нарезанный на
слоты одинакового размера (`buf_len + 1`, округлённое вверх до 64 байт,
поэтому слоты никогда не делят строку кеша), с одним атомарным флагом
владения на слот. Приём захватывает один свободный слот, передаёт ровно
`buf_len` его байт в `recv` устройства и превращает результат в
`PacketBuf`: учтённую ссылку на пул плюс 32-битные смещение и длину, 16 байт
на 64-битных целях. Удаление `PacketBuf` освобождает слот простой записью в
его флаг. Поэтому установившийся поток на этом уровне не выделяет память,
не копирует данные и не берёт блокировку на пакет — на обоих путях. Каждый
поток захватывает слоты через собственный захватчик (acquirer), который
оплачивает ссылки на пул пакетами; поток, владеющий единственным хендлом
своего пула (так всегда у `from_async_device` и `from_device`), захватывает
слот даже без compare-and-swap, а потоки, делящие пул через `*_with_pool`,
— с ним. До этой схемы нативный путь выделял
обнулённый буфер на каждый пакет, а потоковый мост копировал каждый пакет
в новый `Vec` и узел неограниченного канала.

- **Один элемент — один пакет.** Каждый элемент `Ok` — ровно то, что вернул
  `recv`: один IP-пакет (TUN) или один Ethernet-кадр (TAP), никогда не
  фрагмент, не агрегат и не буфер с префиксным заголовком, и никогда не
  длиннее `buf_len` пула. Длина за пределами слота сообщается как
  `BufferTooSmall` одним общим для обоих путей отображением, которое больше
  ничего не решает; какие ошибки завершают поток, решает один приватный
  предикат.
- **Обратное давление вместо роста.** Поток принимает, только пока в его
  пуле есть свободный слот, поэтому принадлежащая ему память ограничена
  пулом (плюс, в потоковом мосте, `sync_channel` с одной ячейкой на слот,
  создаваемым один раз). Удержание всех элементов останавливает поток, а не
  растит очередь; исчерпание слотов — это ожидание, а не ошибка, и таймер
  для него не нужен. Потоки, созданные через `*_with_pool`, могут делить
  один пул и тогда делят его слоты, без какой-либо справедливости между
  ними.
- **Пробуждение.** Нативный поток, не нашедший свободного слота,
  регистрирует свой waker под мьютексом пула — одна запись на ожидающий
  приём, — затем отмечает себя в счётчике ссылок пула и ещё раз проверяет
  слоты. Освобождение уходит на медленный путь под блокировкой и будит его,
  только если ожидающий себя отметил; в остальных случаях освобождение
  обходится без блокировок. Рабочий поток моста вместо этого
  паркуется на condvar, которую освобождение уведомляет, только когда
  рабочий поток действительно запаркован. Ни один waker не клонируется, не
  будится и не удаляется под блокировкой, а каждое пробуждение вне
  собственного `poll_next` потребителя (при освобождении, в рабочем потоке
  или в деструкторе) обёрнуто в `catch_unwind`, поэтому паникующий waker не
  может ни прервать процесс во время раскрутки стека, ни завершить чужой
  поток.
- **Завершение потокового моста.** Удаление потока выставляет флаг
  остановки рабочего потока под мьютексом пула и будит все запаркованные
  рабочие потоки, затем удаляет приёмник канала (который отбрасывает
  элементы в очереди и освобождает их слоты). Рабочий поток, ждущий слот
  или место в канале, завершается сразу; застрявший в блокирующем `recv`
  по-прежнему завершается только после возврата из этого вызова. Как бы ни
  закончился рабочий поток, включая панику в `recv`, он отключает канал и
  будит потребителя, так что поток завершается с `None`.
- **Небезопасный код.** Весь он, вместе со всеми инвариантами, на которые
  опирается, находится в модуле пула: выделение slab, арифметика
  указателей, срезы над одним слотом или одним представлением и
  собственный счётчик ссылок пула (освобождение, которому нужно разбудить
  ожидающего, держит свою ссылку до конца пробуждения, поэтому пул не может
  быть освобождён у него из-под ног). Каждая функция там, создающая или
  меняющая представление, сама проверяет, что оно остаётся внутри своего
  слота, поэтому код вне этого модуля не может нарушить корректность. Его
  тесты также запускаются под Miri в CI.
- **Слоты не обнуляются заново** между пакетами. `PacketBuf` показывает
  только байты, о которых сообщил `recv`; backend, сообщающий о байтах,
  которые он не записал, мог бы раскрыть байты более раннего пакета (см.
  `SECURITY.md`).

Segmentation offload для TUN в Linux сохраняет правило «один элемент —
один пакет»: нарезка при приёме происходит за `recv`, до заполнения слота,
и каждый сегмент занимает один слот, как любой другой приём. Пакетный
приём (несколько пакетов на вызов или на элемент) в дизайн не входит.

Ни один из этих крейтов по умолчанию не зависит от Tokio, async-std или
smol напрямую — фичи `async-io`/`tokio` крейта `tunnel-lattice`
(взаимоисключающие; включение обеих — ошибка компиляции на стороне
`tun-rs`) опциональны, поэтому вызывающий код, не включивший ни одну из
них, вообще не тянет асинхронный рантайм.

## Платформенные и привилегированные особенности

Создание TUN/TAP-устройства обычно требует `CAP_NET_ADMIN` на Linux,
Administrator на Windows или root на macOS/BSD. Флаги `Capability` описывают
реализованные поверхности, а не гарантию того, что текущий процесс
авторизован — вызывающему коду всё равно стоит обрабатывать ошибку
доступа от `DeviceProvider::open`, даже если возможность заявлена как
доступная.

Возможности сообщаются на двух уровнях. Сам backend (`TunRsBackend`,
доступный как `Tunnel::capabilities()`) сообщает, что поддерживает хост до
открытия какого-либо устройства; дескриптор открытого устройства сообщает
тот же ответ плюс флаги, существующие только для дескриптора
(`MAC_MUTATION` у TAP-дескриптора на Linux и macOS,
`SEGMENTATION_OFFLOAD` у TUN-дескриптора в Linux, очередь которого
проверенно использует формат кадров с offload).
`CapabilityProvider::capabilities()` остаётся безошибочным: возможность,
которую backend не может подтвердить, просто отсутствует.

| Флаг | Уровень | Backend `tun-rs` |
|---|---|---|
| `DEVICE_MUTATION` | хост и дескриптор | всегда |
| `PERSISTENT_DEVICES` | хост и дескриптор | Linux |
| `TAP_DEVICES` | хост и дескриптор | зависит от ОС, см. ниже |
| `MULTI_QUEUE` | хост и дескриптор | Linux |
| `NATIVE_ASYNC` | хост и дескриптор | с `async-io` или `tokio` |
| `MAC_MUTATION` | только дескриптор | TAP на Linux и macOS |
| `SEGMENTATION_OFFLOAD` | только дескриптор | очередь TUN в Linux с проверенным форматом кадров offload |

`TAP_DEVICES` зависит от ОС:

| ОС | Как определяется `TAP_DEVICES` |
|---|---|
| Linux | сообщается всегда (драйвер `tun` обслуживает и TUN, и TAP) |
| macOS | сообщается всегда (`feth` встроен в ядро) |
| Windows | сообщается, только если установлен драйвер tap-windows6 (hardware id `tap0901`) |

Ответ на Windows даёт поиск драйвера через SetupAPI, следующий тому, что
`tun-rs` выполняет перед созданием TAP-адаптера (те же проверки hardware id
и версии драйвера, но без выбора драйвера), и останавливающийся до
какой-либо регистрации: он не создаёт адаптер, не требует повышения прав,
выполняется один раз за процесс при первом вызове и кэшируется (драйвер,
установленный позже, будет замечен после перезапуска). Любой из этих
ответов носит рекомендательный характер: `open` никогда не отклоняется
из-за него, а отсутствующий драйвер по-прежнему сообщается самим `open` как
`Error::DriverUnavailable`.
